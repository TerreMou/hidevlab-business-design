# 原始需求澄清

## 目录
1. 核心原则
2. 工作流程（6 阶段）
3. 澄清完成判定（DoD）
4. 输出格式
5. 关键约束
6. 变更记录

## 核心原则
- **1. 提问优先**：绝不假设任何信息，所有细节必须通过提问确认
- **2. 项目代码优先**：结合现有代码理解项目背景和约束
- **3. 结构化输出**：最终输出标准格式的需求分析文档
- **4. 迭代澄清**：通过多轮对话逐层深入，直到需求完全明确

## 工作流程

### 阶段 1：理解项目代码
在进行需求澄清之前，优先理解项目代码，了解项目背景，才能更好的基于已有的业务功能去分析需求。

#### 输出物：项目代码功能报告
阶段 1 必须产出一份"项目代码功能报告"，作为后续澄清的共同上下文：

1. **项目元信息**：仓库地址、技术栈、目录结构概览
2. **已有功能模块清单**：模块名 + 一句话职责 + 关键文件路径
3. **相似功能候选**：与本次需求最相关的 3 个已有功能 + 复用评估
4. **约束与红线**：已发现的技术债、不可改动模块、SOD 既有规则

#### 场景A：用户提到项目中已有功能的需求
优先阅读理解用户提到功能模块的代码。

#### 场景B：用户提到项目中没有的新功能的需求
根据"项目代码功能报告"，了解已有功能，查询相似功能进行需求澄清。

### 阶段 2：需求输入处理
根据用户输入格式选择处理方式：

#### 场景A：用户提供原始需求单号 RR
- 使用 Playwright MCP 工具访问 `https://portal.edevops.huawei.com/raw-requirement/home`
- 搜索并获取需求内容
- 如搜索不到，提示用户确认单号是否正确

#### 场景B：用户提供特性 FE 单号
- 使用 `edevops-mcp-server` 获取需求详情
- 如搜索不到，提示用户确认单号是否正确

#### 场景C：用户提供非结构化需求描述
- 记录用户描述的原始需求
- 进入澄清流程

#### 场景 A/B 失败兜底
若连续 2 次确认后仍搜不到 → 主动询问用户："是否切到场景 C（您直接粘贴需求文本）？"

### 阶段 3：多轮需求澄清
采用系统化提问方式，每次提问聚焦一个主题域。

> **边界条件提示**：每轮至少包含 1 个边界条件问题（空数据 / 超大数据 / 并发竞态 / 权限越权 任选其一）。

#### 第 1 轮：业务背景澄清
- 业务场景是什么？需要解决什么问题？
- 目标用户是谁？他们的使用习惯是什么？
- 现有系统/流程是什么？有哪些痛点？

#### 第 2 轮：功能需求澄清
- 核心功能需求有哪些？
- 功能的输入/输出是什么？
- 功能的关键业务流程是什么？
- 是否有边界条件或异常场景？

#### 第 3 轮：权限矩阵及角色 SOD
- 需求是否涉及新增角色及权限
- 有什么角色权限
- 哪些角色具有 SOD 冲突

#### 第 4 轮：非功能需求澄清
- 性能要求（响应时间、并发数等）？
- 安全性要求？
- 兼容性要求？
- 可用性要求？

#### 第 5 轮：约束与依赖澄清
- 技术栈限制？
- 第三方依赖？
- 时间/资源约束？
- 与其他需求的关联？

## 澄清完成判定（DoD）
满足以下全部条件才能进入阶段 4：

- [ ] 第 1-3 轮的所有子问题已 100% 回复（用户明确不接受某项也算"显式确认"）
- [ ] 至少产出 1 张"权限矩阵"或"角色清单"草稿并经用户确认
- [ ] 用户对"范围边界"明确说"OK / 可以"（口头即可）
- [ ] 业务背景、目标、范围三段已形成可粘贴到 IT 文档的文本

### 阶段 4：需求拆分 RR-FE-US
需求澄清完毕后，将原始需求拆分为特性 FE 及用户故事 US 清单。

### 阶段 5：IT 详细设计文档生成
将澄清后的需求输出为结构化文档，包括：

- 需求概述：业务背景、目标、范围
- 功能需求：用例描述、功能点列表
- 非功能需求：性能、安全、兼容性等
- 约束条件：技术限制、依赖关系
- 待确认项：仍需澄清的问题

#### 文档保存路径
生成的 IT 详细设计文档保存至 **`design/requirements/<需求名>.md`**（需求名使用 kebab-case，例如 `public-project-migration.md`）。首次保存时需 `mkdir -p design/requirements`。

### 阶段 6：用户确认
向用户展示 IT 详细设计文档：

1. 询问是否有遗漏或错误
2. 如有补充，返回相应阶段继续澄清
3. 最后输出 IT 详细设计文档按阶段 5 的保存路径归档

## 关键约束
- 在需求细节未确认前，不得写入任何不确定信息
- 如用户提供的需求不明确，必须持续提问直到完全理解
- 每个澄清问题必须有明确目的，避免无效提问
- 特别注意技术实现约束，这些往往影响需求可行性
